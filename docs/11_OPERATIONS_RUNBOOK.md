## 1. 部署形态与启动（源：设计规范 §7.5）

### 1.1 部署形态

第一版建议单体应用部署，组件如下：

```text
Web Frontend
API Backend
Background Worker
PostgreSQL + pgvector
Object Storage
```

使用 Docker Compose 即可完成课题组内部部署。**第一版不需要 Kubernetes 或微服务架构。**

- 启动命令、端口、环境变量、健康检查与依赖就绪顺序：**Phase 1+ 待补充**（源文档仅规定部署形态，未定义具体命令，本手册不编造）。

## 2. 日常运维职责（源：设计规范 §4.4、§4.3、§8.2、§12 P10、§19.2）

### 2.1 角色分工

- System Administrator：管理账号、权限、模型配置、任务队列、成本和运行状态（（设计规范 §4.4））；
- Curator：维护数据源、处理冲突、合并重复、管理状态和审核队列（（设计规范 §4.3））。

### 2.2 数据源同步

- 每个数据源必须先注册、再允许采集（（设计规范 §8.2）Source Registry）；
- 同步节奏由每个 Source Registry 条目的 `refresh_policy` 决定（示例值：weekly，见（设计规范 §8.2）示例）；
- 手动触发走 Source API（见本文第 4 节）。

### 2.3 审核队列容量上限

- 依据（设计规范 §19.2）控制措施"建立审核容量上限"：为防止低质量自动卡片淹没专家审核能力，须对进入审核队列的候选量设置上限；
- 上限数值与触达上限后的处置动作：**Phase 1+ 待补充**（并已列入《docs/09_RISK_AND_ASSURANCE.md》待裁决问题）。

### 2.4 Stale 降级策略

- 状态机依据（设计规范 §10）：`Published -> Stale -> StatusReview`；
- 触发条件（（设计规范 §12 P10））：超过有效期未核验的问题进入 `Stale`；
- "有效期"数值与 `likely_open` 自动降级为 `Stale` 的具体规则：属（设计规范 §26）第 10 项开放问题（ADR backlog），**Phase 1+ 待补充**。

### 2.5 显著新论文触发

- 依据（设计规范 §12 P10）：检测到显著新论文时，立即触发复核；
- "显著"的判定标准（引用量阈值 / 来源等级 / 关键词命中）：**Phase 1+ 待补充**。

## 3. 周期复核 SOP（源：设计规范 §12 P10）

- **输入**：已发布或已过期问题。
- **执行者**：Scheduler + Status Verification Agent。
- **输出**：更新后的状态或人工复核任务。

建议策略：

| 情形 | 复核频率 |
|---|---|
| 高关注问题 | 每月 |
| 普通问题 | 每季度 |
| 状态不确定问题 | 优先 |
| 检测到显著新论文 | 立即触发 |
| 超过有效期未核验 | 进入 `Stale` |

状态核验本身遵循（设计规范 §12 P4）标准搜索顺序与硬性规则"没有找到证明不等于仍然开放"；未核验声称不得翻转状态的实演见《docs/09_RISK_AND_ASSURANCE.md》第 8 节。

## 4. 管道运行与重试（源：设计规范 §18.4）

### 4.1 Source and Pipeline API 端点

```text
GET    /api/sources
POST   /api/sources
POST   /api/sources/{source_id}/sync
GET    /api/pipeline/runs
GET    /api/pipeline/runs/{run_id}
POST   /api/pipeline/runs/{run_id}/retry
```

所有写接口必须鉴权并记录审计事件（（设计规范 §18.4））。

### 4.2 运行查询与重试

- 通过 `GET /api/pipeline/runs` 巡检采集与加工管道的运行记录；
- 对失败的 run，通过 `POST /api/pipeline/runs/{run_id}/retry` 发起重试；
- 重试的上限次数、退避策略与告警通知：**Phase 1+ 待补充**（源文档未定义）。

## 5. 采集纪律与合规（源：设计规范 §8.3、§12 P0）

### 5.1 采集要求（设计规范 §8.3，逐条保留）

- 遵守 API 速率限制、许可与署名要求；
- 保存原始响应或内容指纹；
- 记录采集时间和 Connector 版本；
- 数据源删除内容时不得立即物理删除本地证据；
- 外部网页内容一律视为不可信输入；
- 外部文本不得改变 Agent 系统指令、工具权限或发布策略。

### 5.2 来源注册门禁（设计规范 §12 P0）

- 新数据源启用前必须完成 P0 数据源注册 SOP（8 个步骤，含连接器契约测试与人工批准）；
- 硬失败条件：来源身份不明、许可不允许、无法保存原始证据。

### 5.3 隐私与审计合规

- 审计日志不得泄露模型私密凭据或完整敏感输入（（设计规范 §19.4））；
- 内部问题默认不得发送给未经批准的外部模型（（设计规范 §19.4））。

## 6. 成本与模型配置管理（源：设计规范 §19.2、§9.1、§11.2、§20.4、§14.3）

### 6.1 版本化要求

- 对模型、rubric 和特征做版本化（（设计规范 §19.2）控制措施）；
- 重要性 / AI 友好性评估均携带 `rubric_version` 字段（（设计规范 §9.1））；
- 所有模型版本、提示词版本、工具调用和输入证据必须记录（（设计规范 §11.2）执行纪律第 10 条）。

### 6.2 成本观测

- Agent 指标包含"每张可发布卡的成本和时间"（（设计规范 §20.4），评测口径见《docs/10_EVALUATION_PLAN.md》第 5 节）；
- 求解类预算字段（tokens / wall_time / monetary_cost / parallel_runs）属（设计规范 §14.3）Phase 5 范畴，本版仅保留接口预留。

### 6.3 旧评分漂移处置（本手册约定，承接 §19.2 P1 风险）

风险（（设计规范 §19.2））：模型升级导致旧评分漂移。处置约定：

1. 模型或 rubric 升级时，由旧版本模型 / rubric 产生的评分标记为 `superseded`；
2. 被标记评分按"定期抽样复核"（（设计规范 §19.2）控制措施）计划重新核验；
3. `superseded` 标记的数据模型落点（评分字段当前 Schema 未含状态位）：**Phase 1+ 待补充**。

## 7. 升级与回滚（源：设计规范 §7.2、§21.2、§9.1、§24.3）

### 7.1 版本控制

- 全程使用 git 管理变更；禁止"没有迁移、回滚和版本记录地修改数据库"（（设计规范 §24.3）禁止的开发方式）。

### 7.2 数据库迁移

- 使用 Alembic 管理迁移（（设计规范 §7.2）技术栈）；
- 数据库迁移向后兼容属于契约测试范围（（设计规范 §21.2））。

### 7.3 Schema 版本兼容

- Problem Card 等核心实体携带 `schema_version`（（设计规范 §9.1））；
- 仓库已落盘 6 个 JSON Schema：`schemas/problem_card`、`schemas/evidence`、`schemas/review`、`schemas/attempt`、`schemas/source_registry`、`schemas/agent_task_contract`；
- Schema 变更须保证旧版本卡片的读取兼容；具体兼容矩阵：**Phase 1+ 待补充**。
